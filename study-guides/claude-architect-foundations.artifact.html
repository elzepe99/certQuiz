01The exam, factually

A small, accurate deck for a wide exam

The deck is sound, and where it teaches, it teaches the exam's own phrasing. But 28 questions cannot cover 30 task statements, and they do not try evenly: tool design has twelve, Claude Code has two, agentic architecture has two. Read §2 before you drill, and treat §3, §5, §6 and §7 as the main course rather than the appendix.

How the outline was found — the part that generalises

Anthropic publishes the outline in the open, the way Databricks does. The certification page on the Anthropic Academy (a Skilljar site) carries the five domain weights, the item count, the time, the fee and the pass mark as plain text, and links an exam guide PDF hosted on S3. The PDF is the one that matters: it holds the 30 task statements, each split into "Knowledge of" and "Skills in" bullets, plus the six scenarios, twelve sample questions, and an explicit in-scope and out-of-scope list. The out-of-scope list is a distractor filter

03Agentic Architecture & Orchestration

27% of the exam — about 16 questions — and two deck items: parallel subagents and a hook that blocks refunds over $500. Both are right and both are worth knowing cold. Everything else in this section is new.

1.1 · The agentic loop

Send the request; read stop_reason. If it is tool_use, run the tool, append the tool_result to the conversation, and call again. If it is end_turn, Claude has finished — use the response. The Stop reasons page lists these alongside max_tokens, stop_sequence, pause_turn (a server-tool loop hit its iteration limit; send the content back to continue) and refusal.

The three anti-patterns the guide names

Deciding the loop is done by parsing Claude's text for "I'm finished"; using an iteration cap as the primary stop; and treating the presence of assistant text as completion. A response can carry text and a tool_use block. Any option built on one of these is the distractor.

1.2 · Coordinator and subagents

  • Hub and spoke. All inter-subagent traffic, error handling and routing go through the coordinator — for observability and consistent recovery.
  • Subagents do not inherit the coordinator's history. "Each subagent runs in its own conversation, which starts fresh." Whatever it needs goes into its prompt.
  • Pick subagents per query rather than always running the full pipeline, and partition scope (distinct subtopics or source types) to avoid duplication.
  • Iterate: the coordinator checks synthesis for gaps, re-delegates targeted queries, re-runs synthesis.
The failure the exam loves: decomposition too narrow

Sample question 7 in the guide: every subagent succeeds, yet a report on "AI in creative industries" covers only visual arts. The coordinator's log shows three visual-arts subtasks. The root cause is the coordinator's decomposition, not search, analysis or synthesis — they did what they were told. When the logs show the plan, blame the plan.

1.3 · Spawning and context passing — the deck's one item

Subagents are spawned through a tool the exam guide calls Task and the current SDK calls Agent (§11). The coordinator's allowed tools must include it. To run two subagents in parallel, emit both calls in one response; consecutive turns serialise them. Pass prior findings in the prompt, as structured data that separates content from metadata (URL, document, page), and give the coordinator goals and quality criteria rather than a step-by-step procedure. AgentDefinition holds each subagent's description, prompt and tool list.

1.4 · Enforcement and handoff

When ordering matters for money or identity, prompt instructions have a non-zero failure rate. Make it programmatic: block process_refund until get_customer has returned a verified id. This is the guide's sample question 1, and the prompt-only and few-shot options are the distractors. When escalating to a human who cannot see the transcript, send a structured handoff: customer id, root cause, amount, recommended action.

1.5 · Hooks

PreToolUse fires before a tool runs and can block it by returning permissionDecision: "deny" — the $500 refund rule. PostToolUse fires after a tool returns and can rewrite the result before Claude sees it, which is how you normalise Unix timestamps, ISO 8601 and numeric status codes from different MCP servers into one shape. The deciding phrase in a stem is "guaranteed" or "must": that wants a hook, not a prompt.

1.6 · Decomposition

PatternUse it when
Prompt chaining (fixed sequence)The steps are predictable — review each file, then run one cross-file integration pass
Dynamic decompositionThe work is open-ended — "add tests to a legacy codebase": map structure, find high-impact areas, plan, adapt as dependencies appear

1.7 · Sessions

  • --resume continues a named prior session; add --fork-session (or fork_session=True in the SDK) to branch it under a new session id — two refactoring approaches from one analysis.
  • Resume when the prior context is still valid; start fresh with an injected summary when the tool results are stale. If files changed since, tell the resumed session which ones, so it re-reads those rather than everything.

04Tool Design & MCP Integration

18% of the exam — about 11 questions — and 12 deck items, the deck's home ground. Tool interfaces (2.1) and structured errors (2.2) are drilled thoroughly. Tool distribution (2.3) and built-in tools (2.5) are not drilled at all.

2.1 · Descriptions are the selection mechanism

"Provide extremely detailed descriptions. This is by far the most important factor in tool performance." Include input formats, example queries, edge cases, and when to use this tool rather than its neighbour. The deck drills this four ways: descriptions over schema constraints, accepting the id the caller already has, a composite tool that keeps the judgment with the agent, and showing the full input in the confirmation. Splitting and consolidating have a section of their own — §8.

Check the system prompt, not just the tools

The guide names a failure the deck does not: keyword-sensitive wording in the system prompt that pulls the model toward the wrong tool and overrides good descriptions. When descriptions are already good and selection is still wrong, read the system prompt.

2.2 · Structured errors — five deck items

Return the failure as a tool result with isError: true, carrying an errorCategory (transient / validation / permission / business), an isRetryable flag and a readable message. MCP separates two channels: a malformed request is a JSON-RPC protocol error; an API failure or business rule is a tool result with isError. And a valid empty result is not an error — "no orders found" is a successful query.

2.3 · How many tools, and tool_choice — not in the deck

  • Scope tools by role. The guide's number: an agent with 18 tools instead of 4–5 selects worse. A synthesis agent with web-search tools will search. Give a narrowly scoped cross-role tool for the frequent case (a verify_fact for synthesis, sample question 9) and route the rest through the coordinator.
  • Replace generic tools with constrained ones — a load_document that validates URLs instead of a bare fetch_url.
tool_choiceEffect
autoClaude may call a tool or answer in text. Default when tools are provided
anyClaude must call a tool, but chooses which — guarantees structured output when the document type is unknown
{"type":"tool","name":…}Claude must call that tool — forcing extract_metadata to run first
noneNo tools. Default when none are provided

Forced modes (any, named tool) are not supported with manual extended thinking; auto and none still work.

2.4 · MCP servers in Claude Code

Shared team servers go in .mcp.json at the project root, committed, with secrets as ${GITHUB_TOKEN}-style expansion rather than literals. Personal or experimental servers go in ~/.claude.json. Every configured server's tools are discovered at connection and available at once. Prefer an existing community server for a standard integration like Jira; expose catalogues (schemas, issue summaries) as MCP resources so the agent can see what exists without exploratory calls; and if the agent keeps using Grep instead of your better MCP tool, the fix is the MCP tool's description.

2.5 · Built-in tools

ToolFor
GrepSearching file contents — callers of a function, an error string
GlobFinding files by path pattern — **/*.test.tsx
Read / WriteWhole files. Read + Write is the fallback when Edit cannot find a unique anchor
EditTargeted change by unique text match

Build understanding incrementally: Grep for the entry point, Read to follow imports — not read everything up front.

05Claude Code Configuration & Workflows

20% of the exam — about 12 questions — and two deck items: a project skill committed under .claude/skills/, and --bare in CI. Four of this domain's six task statements have nothing.

3.1 · The CLAUDE.md hierarchy

LevelLocationShared with
User~/.claude/CLAUDE.mdJust you, all projects — never reaches teammates
Project./CLAUDE.md or ./.claude/CLAUDE.mdThe team, via version control
Directorya CLAUDE.md in a subdirectoryThe team; loads for that subtree

The diagnosis the exam wants: a new team member is not getting the instructions because they live in someone's user-level file. Move them to the project file. Keep the file modular with @path/to/file imports, or split it into topic files under .claude/rules/. Use /memory to see which memory files actually loaded. (The docs add two levels the exam does not ask about: an organisation-wide managed policy file, and CLAUDE.local.md for personal project notes.)

3.2 · Commands and skills

  • Project commands in .claude/commands/ and skills in .claude/skills/<name>/SKILL.md are shared through the repo; the user versions live under ~/.claude/. Sample question 4: a team /review command goes in the project's .claude/commands/.
  • Skill frontmatter: context: fork runs the skill in its own subagent context so verbose output does not flood the session; allowed-tools governs tools during the skill (see §11 on what it now means); argument-hint prompts for the argument.
  • Skill versus CLAUDE.md: a skill is invoked on demand for a task; CLAUDE.md is always loaded, for standards that always apply.

3.3 · Path-specific rules

A file in .claude/rules/ with a paths: list of globs in its YAML frontmatter loads only when Claude works on matching files. That beats a subdirectory CLAUDE.md whenever the files are scattered — test files living next to the code they test are the canonical case (sample question 6). A skill is wrong there too: it is not applied automatically by path.

3.4 · Plan mode or direct execution

Plan mode "tells Claude to research and propose changes without making them" — it reads and explores, writes a plan, and edits stay blocked until you approve. Use it for architectural work, many files, or several valid approaches (a monolith split, a 45-file library migration). Use direct execution for a well-scoped change (one-file fix with a stack trace). The guide's sample question 5 rejects "start direct and switch if it gets complicated" — the complexity was stated up front. The Explore subagent keeps verbose discovery out of the main context.

3.5 · Iterative refinement

  • When prose instructions are read inconsistently, give 2–3 concrete input/output examples.
  • Test-driven iteration: write the tests first, then feed Claude the failures.
  • The interview pattern: have Claude ask you questions before it builds in an unfamiliar domain.
  • Interacting problems in one message; independent problems one at a time.

3.6 · CI/CD — one deck item, and the flags it does not use

FlagWhy CI needs it
-p / --printNon-interactive: without it the job hangs waiting for input (sample question 10). CLAUDE_HEADLESS and --batch do not exist
--output-format jsonMachine-readable output
--json-schemaValidated JSON matching a schema — findings you can post as inline PR comments
--bareSkips discovery of hooks, skills, plugins, MCP servers and CLAUDE.md for fast start; pair it with --append-system-prompt-file to put the standards back

In the exam guide's own model, CLAUDE.md is how CI-invoked Claude Code gets project context — testing standards, fixtures, review criteria. --bare is newer than that model; if a stem has no startup-time problem, CLAUDE.md is the answer. Two more CI skills: on a re-run, include the prior findings and ask only for new or unaddressed issues; and give test generation the existing tests so it does not duplicate them.

06Prompt Engineering & Structured Output

20% of the exam — about 12 questions. The deck's two on-outline items are few-shot examples against false positives and specifying the JSON schema. This domain is where Scenario 6, which the deck never uses, does most of its asking.

4.1 · Explicit criteria beat "be careful"

"Flag a comment only when its claimed behaviour contradicts the code" works; "check comments are accurate" or "only report high-confidence findings" does not. Write which categories to report and which to skip. When one category floods developers with false positives, turn it off while you fix it — noisy categories erode trust in the accurate ones.

4.2 · Few-shot

The guide calls few-shot "the most effective technique" when instructions alone give inconsistent output. Use 2–4 targeted examples for the ambiguous cases, each showing why one action beat the plausible alternative. Anthropic's prompting page says 3–5 and "cover edge cases" — the same advice at a slightly different count.

4.3 · Structured output with tool_use

  • A tool whose input schema is the output you want is the most reliable way to get schema-compliant JSON. It eliminates syntax errors, not semantic ones — line items that do not sum to the total still get through.
  • Make a field optional or nullable when the source may not contain it, or the model will invent a value to satisfy required.
  • For extensible categories use an enum with "other" plus a detail string, and add "unclear" for genuinely ambiguous input.

4.4 · Validation and retry

On a failed validation, send back the document, the failed extraction and the specific error. That fixes format and structure. It cannot fix absence: if the value is only in a document you did not provide, retrying burns tokens. For self-checks, extract calculated_total beside stated_total, and add a conflict_detected flag.

4.5 · The Message Batches API

Cost50% of standard
LatencyMost finish within an hour; no SLA; a batch expires if not done in 24 hours
SizeUp to 100,000 requests or 256 MB
ResultsKept 29 days; correlate by custom_id (1–64 characters)
CannotRun multi-turn tool calling inside one request

So: overnight reports yes, blocking pre-merge checks no (sample question 11). Resubmit only the failed custom_ids, chunking any that overflowed. To meet a 30-hour SLA with a 24-hour window, submit every 4 hours. Refine the prompt on a sample before sending the bulk.

4.6 · Multi-instance review

A model reviewing its own output in the same session keeps its reasoning and rarely questions it. An independent instance without that context catches more — more than "review your work carefully" or extended thinking. For a large PR, per-file passes plus one integration pass (sample question 12); a bigger context window does not fix attention dilution.

07Context Management & Reliability

15% of the exam — about 9 questions — and six deck items, proportionally the deck's best-covered domain. It is also where four items that look like pure judgment turn out to be settled by the exam guide itself.

Four "unsettleable" items, settled by the blueprint

Four deck items — on source dates, claim-source mappings, frustrated customers and escalation triggers — read as agent-design judgment that no product page decides. That is true of the documentation. The exam guide states each keyed answer almost verbatim: 5.6 "requiring subagents to include publication or data collection dates" and "structured claim-source mappings"; 5.2 "acknowledging frustration while offering resolution" and escalation on "customer requests for a human, policy exceptions/gaps… and inability to make meaningful progress". On this exam, those four are fact.

5.1 · Long conversations

Summaries flatten numbers, dates and promises. Keep a "case facts" block of amounts, dates, order ids and statuses outside the summarised history, one per issue in a multi-issue session. Trim tool results to the fields you need (5 of 40, not 40). Put key findings first in long inputs — the middle is where models lose things.

5.2 · Escalation

  • Escalate when the customer asks for a human, when policy is silent or needs an exception (competitor price-matching when policy covers only your own site), or when you cannot make progress.
  • An explicit demand for a human is honoured immediately, without investigating first. Frustration is not a demand: acknowledge it, offer the resolution you can give, escalate if they ask again. One deck item sits right on this line and keys the second.
  • Several matching customers: ask for another identifier; never pick by heuristic.
  • Sentiment scores and self-reported confidence are poor proxies for complexity (sample question 3).

5.3 · Error propagation between agents — not in the deck

A subagent that fails should hand the coordinator the failure type, what it tried, any partial results, and alternatives (sample question 8). It should retry transient failures itself first. Two anti-patterns are equally wrong: returning an empty result marked as success, and killing the whole workflow on one timeout. Synthesis should annotate which areas are thin because a source was unavailable.

5.4 · Big codebases

Context degradation shows up as vague answers about "typical patterns" instead of the classes found earlier. Delegate specific questions to subagents, keep a scratchpad file of findings, summarise a phase before starting the next, export state to a manifest for crash recovery, and /compact when discovery output fills the window.

5.5 · Human review and calibration — not in the deck

97% overall can hide a document type at 60%. Measure accuracy by document type and field before cutting human review. Keep a stratified random sample of high-confidence extractions under review to catch new error patterns. Have the model emit field-level confidence, then set thresholds against a labelled validation set — calibrated, not taken at face value.

5.6 · Provenance

Carry claim-to-source mappings through every step; require dates so old and new figures are not read as a contradiction; when credible sources conflict, keep both values with attribution rather than choosing; and render financial data as tables, news as prose.

08Split or consolidate: the tension in the guidance

Two deck items key opposite moves on tool count, and both are correct. This is the most useful thing the deck teaches, because the exam lists "splitting vs consolidating tools" as an in-scope topic by name.

SplitConsolidate
SymptomOne tool for refund / cancel / reship; the agent omits required parameters or adds irrelevant onesTen tools; the agent picks the wrong one between near-synonyms
KeyThree tools, each declaring only its own parametersMerge overlapping pairs behind an action parameter
What it buysParameter accuracy — each required array means somethingSelection accuracy — fewer competing definitions
Guidance behind it"Make sure each tool you build has a clear, distinct purpose" (Writing tools for agents)"Fewer, more capable tools reduce selection ambiguity" (Define tools)
The rule

Read the symptom. Wrong or missing arguments → split, so each schema is small and exact. Wrong tool among overlapping ones → consolidate or rename. An option is only wrong if it claims one move buys both.

But "first step" changes the answer

The exam guide's sample question 2 is a selection problem between two tools with minimal descriptions, and it keys better descriptions. It calls consolidation "a valid architectural choice" that "requires more effort than a first step warrants". Task statement 2.1 also names renaming an overlapping tool and rewriting its description as the fix. So consolidation wins when the stem asks what structurally eliminates overlap; descriptions win when it asks for the first or most effective step and the descriptions are thin.

A third item makes the same point from a different angle: it merges discovery and analysis into one tool but keeps add to collection separate, because the agent must still make the editorial choice. Consolidate the mechanics; leave the judgment callable.

10Distractor tells

Read the question's own verb

"Most effective first step" wants the cheap, proportionate fix — descriptions, explicit criteria, few-shot — before a classifier or new infrastructure. "Guarantee" or "must" wants code: a hook, a prerequisite gate, forced tool_choice. "Root cause" wants the component whose logs show the fault, not the one downstream of it.

  • Prompt-only enforcement of a money or identity rule. Always the distractor when a hook or gate is offered.
  • Over-engineering. A routing classifier, a separately trained model, or a sentiment pipeline where a description or criterion change would do. The guide's own answer explanations call these out repeatedly.
  • "Bigger context window." Never fixes attention dilution or lost-in-the-middle.
  • Self-reported confidence as a router. Wrong for escalation (poorly calibrated). Right only as field-level confidence calibrated on labelled data for review routing. Watch which one the option describes.
  • Swallowing an error as an empty success, or aborting everything on one failure. Both wrong.
  • A flag or setting that does not exist. CLAUDE_HEADLESS, --batch, a .claude/config.json commands array — the guide's own distractors. If you cannot picture it in the docs, distrust it.
  • User-level configuration for a team problem. ~/.claude/ is personal; the team's copy is in the repo.

11Where the exam and the product disagree

The deck is not older than the exam. But the exam guide was frozen in July 2026 and Claude Code ships weekly, so the exam and the current docs already disagree in five places. None moves a deck key. Answer the exam in its own vocabulary; know the product's.

TopicThe exam guide saysThe docs now say
Spawning subagentsThe Task tool; allowedTools must include "Task"The Agent tool since Claude Code v2.1.63; examples allow "Agent". The system:init tool list still says Task
Skill allowed-toolsRestricts tool access during the skillTools Claude may use without asking — a pre-approval. Removing tools is disallowed-tools
Commands.claude/commands/ and skills as separate things"Custom commands have been merged into skills"; old command files still work
MCP scopesTwo: project (.mcp.json) and user (~/.claude.json)Three: local is the default, stored in ~/.claude.json under the project path
How many tools is too many18 instead of 4–5, per agentSelection degrades past 30–50 available tools, where tool search helps
The last row is two different questions, not a contradiction

The exam's 4–5 is about role scoping: a specialist agent should hold only its own tools. The docs' 30–50 is about catalogue size: when the whole set gets that large, defer loading and let the model search. The deck's consolidation item uses the second number correctly to reject tool search for a ten-tool agent.

Exam-right, product-wrong: allowed-tools

If an exam item asks how to stop a skill running destructive commands, the guide's intended answer is allowed-tools in the frontmatter. In a current Claude Code, that field grants tools for the turn; the field that removes them is disallowed-tools. No deck item touches this, so nothing needs fixing here — but do not carry the exam's reading into a real project.

12Two-week revision plan

The deck takes an hour to work through, so it cannot anchor two weeks. The plan follows the exam's weights and uses the deck twice: once early as a diagnostic, once at the end. The Exercises in section 8 of the exam guide are the best practice material that exists — build them.

Week 1 — the half of the exam the deck does not reach

  1. Day 1 · Diagnostic. Read the exam guide's sections 4–6 end to end. Do all 28 deck questions and all 12 sample questions. Note every miss.
  2. Day 2–3 · Agentic architecture. §3. Write an agentic loop by hand on stop_reason. Build the guide's Exercise 1: tools, a hook blocking over a threshold, a multi-concern request.
  3. Day 4–5 · Claude Code. §5. Do Exercise 2 on a real repo: project CLAUDE.md, a @ import, two .claude/rules/ files with paths:, a skill with context: fork, a .mcp.json with an env-var token. Try plan mode on a multi-file change.
  4. Day 6 · Structured extraction. §6. Exercise 3: a nullable schema, a validation-retry loop, a batch of documents by custom_id. This is Scenario 6.
  5. Day 7 · Consolidate. Re-read §9 and §10.

Week 2 — the rest, then the deck again

  1. Day 8 · Multi-agent research. Exercise 4: parallel subagents, structured errors from a timed-out subagent, conflicting sources kept with attribution.
  2. Day 9 · Context and reliability. §7, especially 5.3 and 5.5, which the deck does not test.
  3. Day 10 · Tool design. §4 and §8. The deck's twelve tool items, then write the split-or-consolidate rule from memory.
  4. Day 11 · §11 in full, and the out-of-scope list in §1.
  5. Day 12 · The sample questions again, reading only the explanations of the wrong options.
  6. Day 13 · Full deck in Blitz mode, options read aloud off.
  7. Day 14 · Only the misses, and the uncovered-task table in §2 as a checklist.
